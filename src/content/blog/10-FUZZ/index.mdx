### 痛点
- **生成的测试不够好**：现有 fuzzer 主要依靠随机变异或启发式规则，抓不住 ISA 里指令之间的依赖关系，因此产生大量重复用例，边界情况没有被探索到；论文还明确指出，先前工具有时生成的用例里可执行指令甚至不到 10 条。
- **优化效率不高**：有些工作用控制流引导或强化学习来挑选用例，但“改进用例”和“探索覆盖”混在一起，导致两边效率都不高。
- **算力开销大**：每次迭代都要在周期级精度的 DUT 仿真上运行一大批用例，速度慢到限制探索范围。

### 方法

- **用 Golden Reference Model 代替昂贵的 DUT 做前期反馈**
  不需要每生成一个测试都去跑很慢的 RTL 仿真，而是在更快的参考模型上评估测试质量。**降低生成高质量测试的成本。**

- **以 Instruction Block 为单位生成和优化测试**
  不只是随机拼单条指令，而是关注**一组指令之间的组合与依赖关系**，逐步构造高质量测试用例。**让生成的指令序列更有意义。**

- **利用好/坏测试的反馈持续优化，再拿高质量测试去测真实 DUT**
  根据覆盖率等反馈判断哪些指令组合有效、哪些效果差，用这些信息改进后续生成，最后把优化后的测试用于真实 CPU。**先快速学会“怎么测”，再真正去“测 CPU、找 Bug”。**

### 局限

1. **依赖高质量的 GRM。** GoldenFuzz 的核心前提是存在一个快速、可信、ISA-compliant 的 Golden Reference Model。如果换到某种新 ISA、定制扩展或特殊硬件，而没有成熟 GRM，那么这套方法就不容易直接使用。**GRM 自己如果存在错误，也可能影响测试生成和判断**。

2. **GRM 和真实 DUT 存在“抽象鸿沟”。** GRM 主要描述 ISA 层面的正确行为，而真正 CPU 还有 Pipeline、Cache、Branch Predictor、乱序执行等复杂微架构状态。**在 GRM 上表现“好”的测试，不一定就是最能探索 DUT 微架构状态的测试。** GoldenFuzz 本身采用“两阶段”设计，只是把测试 refinement 与 DUT 上的 coverage/vulnerability exploration **部分解耦**，并没有完全替代 DUT fuzzing。

3. **Coverage 只是代理指标，不等于 Bug。** GoldenFuzz 很重视覆盖率，因为它需要一个信号判断测试有没有探索价值。Coverage 高只能说明“探索得广/深了一些”，不能保证一定进入了真正容易出 Bug 的状态。更一般的 coverage-guided fuzzing 研究也指出，只知道“执行了哪里”有时不足以描述“以什么状态、什么路径到达那里”。可能存在：

   ```text
   Test A → Coverage 很高 → 没 Bug
   Test B → Coverage 不突出 → 恰好触发关键 Bug
   ```

4. **目前验证范围仍然有限。** 论文主要在 RocketChip、BOOM、CVA6 三个 RISC-V 处理器上评估，并额外测试了商业 BA51-H core extension；结果很好，但这并不能直接证明它对所有处理器、所有 ISA 和各种定制硬件都同样有效。
